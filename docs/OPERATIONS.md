# Operating Slow Reveal Studio

## Current safety boundary

The studio is a prototype until real canvas/ink/marker tests, costs, packaging and operational checks are approved. Example prices are development fixtures. Setting flags is an operator assertion, not evidence that physical tests passed. The app cannot validate a physical product remotely. Labs and private design saving work without payment services. Production checkout fails closed unless every service and physical gate is configured and the database catalogue is approved.

## Local development

Copy `.env.example` to `.env.local`. For local administrator access, explicitly set `ALLOW_LOCAL_ADMIN_TOKEN=true`, generate a private `ADMIN_API_TOKEN` of at least 32 base64url characters and enter it in `/admin`. Both the configured site and request must use an exact loopback hostname. Production-build QA additionally requires `ALLOW_LOCAL_DEVELOPMENT_STORAGE=true`. This fallback never satisfies the production administrator launch gate and has no remote production emergency mode. No default password or unauthenticated administrator route exists, even on localhost. Run `npm run dev`; bind to loopback. Saved photos and records are under `.data/`, outside `public/`, ignored by Git. Do not put this folder on a public share or deploy its contents. This adapter is single-process development storage. Production requires Supabase and R2; disable both local opt-ins on public hosts.

## Deployment configuration

1. Create a Supabase project and apply all migrations in `supabase/migrations/`, including `202609270003_customer_proofs.sql` for append-only customer proof attestations and `202609280004_admin_presets.sql` for active administrator membership and immutable preset history. Keep the service-role credential server-only. All app tables have RLS enabled and anonymous/authenticated privileges revoked. The HTTP API owns access control; users cannot read photos, grant themselves roles or modify preset versions directly through Supabase.
2. Create an R2 bucket with all public access disabled. Scope its token to this bucket. Supply the four R2 environment variables. Allow CORS GET/HEAD/PUT from the exact website origin and the `Content-Type`, `Content-Length`, `If-None-Match` request headers. No permanent public photo URLs are created. Authenticated source/file requests redirect to signed GET URLs valid for 60 seconds; treat those temporary URLs as private capabilities. Large originals use a two-minute presigned upload ticket and a 15-minute finalisation window. Finalisation rechecks bytes, magic signature, MIME, decoded dimensions and ownership before copying to a permanent immutable source. Configure an R2 lifecycle rule to expire `staging/` after one day as a fallback for abandoned or late upload tickets.
3. Configure Resend with a verified sending domain and `RESEND_FROM_EMAIL`. Check spam handling and customer-support replies. Saved-design email is sent only if an email address is explicitly supplied to save. Order/dispatch/request-photo/revised-proof mail uses plain text and a durable notification record with a stable provider idempotency key. Failed delivery preserves the successful order update and returns the notification's pending/sending state; operators retry that notification without repeating dispatch or regenerating artwork. Confirmations retry through Stripe webhook retries or the same operator action. Persisted sent markers prevent later webhook replays from resending old confirmation messages, even after the provider's own idempotency window. No tests send real email.
4. Configure Stripe, with a distinct test and live setup. Point its webhook to `/api/stripe/webhook`; subscribe to `checkout.session.completed` and `checkout.session.async_payment_succeeded`. Raw body signatures are verified, then session identity, snapshot hash, currency and amount are checked. Session redirects never create a paid order. Test duplicate delivery, delayed methods, invalid signatures, checkout retries and mail-provider failures before enabling real money.
5. Replace prototype catalogue costs and finishes in `studio_catalogue.definition`. Review UK tax and delivery treatment, establish inventory, and set `prototype:false` only after commercial approval. Prices in requests are ignored; the server quotes from this catalogue. Fixed UK shipping tiers are £5.95/£9.95 development values; update the authoritative catalogue code before launch. Stripe promotion codes are supported; the verified discount is checked against the quoted total.
6. Set a canonical HTTPS `NEXT_PUBLIC_SITE_URL`, complete physical tests, record their evidence, then set `PHYSICAL_VALIDATION_APPROVED=true`, appropriate `PHYSICALLY_VALIDATED_MODES` and `LIVE_CHECKOUT_ENABLED=true`. Inverted/dark-canvas checkout remains blocked because a white-ink production separation is not implemented. Never enable a mode solely because its screen preview looks attractive.
7. Configure `RATE_LIMIT_SECRET` and host-level request/body limits before public access. Ingress must replace client-supplied forwarding headers. The server uses daily keyed hashes of an ingress IP, never stores/logs raw IP addresses, and enforces atomic Supabase quotas: ten saves/uploads per 15 minutes, 60 expensive previews per 15 minutes, and 200 saves/upload tickets per deployment/day. Checkout is limited before heavy production rendering: five attempts per ingress IP/15 minutes, 50 per deployment/day, and three per saved design/hour. Local development uses bounded in-memory counters. These small initial quotas protect the prototype; tune deliberately after measured use. Save endpoints cap image uploads at 8 MB and 40 megapixels, reject MIME/signature mismatches, and reject animated or extreme-aspect inputs. Same-origin checking is CSRF protection, not bot protection. No image data, customer details or secrets are logged by app handlers.
8. Configure a separate random `CRON_SECRET` and schedule `GET /api/cron/retention` daily (for example 04:00 UTC), with `Authorization: Bearer <CRON_SECRET>`. Vercel cron adds this header from its environment. The job deletes expired staging tickets, analytics older than 90 days, expired unpaid designs and abandoned checkouts only after Stripe confirms the session is expired and unpaid (seven-day grace). Unknown sessions stay for manual review. A configured secret alone does not prove the scheduler ran: verify the first execution and monitor failures. Paid sources are copied into per-order/revision storage so erasure cannot break another order. Legacy shared references are preserved if any other checkout/order still needs them.
9. Configure `ORDER_ACCESS_KEYS` as a server-only JSON keyring, for example `{"v1":"<independent random secret of at least 32 characters>"}`, and set `ORDER_ACCESS_KEY_ID=v1`. New order capabilities are HMAC-SHA-256 values derived from the order ID and selected key; the database stores only a key ID and capability hash. Confirmation/status messages reconstruct the private `/order/:id#token=...` link in memory when sending, so the outbox never stores raw access tokens. For rotation, add a new named key, change the active ID, and retain earlier keys while their orders need email access. Replacing/removing an old key prevents reconstruction of those old links; restore it from secure secret storage before retrying notifications. Existing customer links still authenticate against their recorded hashes. Never log environment keyrings or email bodies. Legacy development orders without a retained key ID need manual access-link recovery rather than inventing a new token.

## Administrator identities and shared presets

Set `SUPABASE_ADMIN_AUTH_ENABLED=true` and matching `SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_URL` for the same project. Supply a publishable key in `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (a legacy `anon` key is accepted). The server refuses mismatched origins, remote HTTP, credential-bearing URLs and service-role/secret browser keys. Only this validated public configuration reaches the login component. Keep `SUPABASE_SERVICE_ROLE_KEY` server-only.

Provision staff accounts through the Supabase dashboard, then explicitly insert each existing Auth user UUID into `studio_admin_users` with `role='reviewer'` or `role='operator'` and `active=true`. The app has no signup, invitation, automatic role grant or user-management API. Use Supabase's account recovery procedures. Disable a staff membership with `active=false` to deny its next API request even if its access token has not expired. Membership changes and initial access must be verified against the real deployment before launch; local tests use provider stubs and do not provision users.

The browser signs in through the Supabase SDK and keeps the session in memory. Administrator API requests carry its access JWT in `Authorization`; the server calls `auth.getUser(jwt)` and then reads the private active membership row on every request. It never authorises using browser session metadata or a decoded role claim. No access/refresh token or email address is added to application records. Order review and artwork-erasure audit entries record the verified user ID and authentication kind; preset versions and publication history do the same. Shared local QA credentials are attributed only as `local-development`.

| Action                                                                                        | Reviewer | Operator |
| --------------------------------------------------------------------------------------------- | -------- | -------- |
| Inspect orders, private artwork and analytics                                                 | Yes      | Yes      |
| Hold, request an alternate photo, regenerate, approve artwork, retry an existing notification | Yes      | Yes      |
| Dispatch, erase dispatched artwork, run retention                                             | No       | Yes      |
| Read shared preset history, create drafts, append draft versions                              | Yes      | Yes      |
| Publish, unpublish, archive or restore a shared preset                                        | No       | Yes      |

Shared presets are versioned records in the private Supabase `studio_records` collection with `kind='presets'`; local development persists the same format under `.data/presets/`. Edits append immutable versions and require the latest record revision. Publication points to one specific existing version and is a separate operator action. Saving a draft leaves the current public version unchanged. Archive removes the public version; restore does not republish. The public API projects only the chosen name, description, mode, numeric/boolean renderer controls, palette, cell shape and renderer version. Presets never carry customer photos, crops, personalisation, selected product dimensions, ink, customer details or administrator IDs. Name/description are deliberately public editorial copy: never paste customer data into them.

Both publication and public reads reject/hide obsolete renderer versions and mode mismatches. After a renderer upgrade, append and review a new preset version before publishing. Public mode availability still follows the physical-validation gate; publishing an experimental mode does not make it available for customer checkout. Existing paid artwork remains its own immutable settings/geometry snapshot. Presets have up to 100 versions; create a new named preset when that history limit is reached. Create/update quotas are 30/60 requests per administrator per hour.

Manual subject selections are private photo-derived artwork, not presets. Shared preset writes reject `subjectMaskStrength` and mask payloads; applying a preset preserves the customer's own current selection. A design may submit a version-1 `cropped-v1` alpha8 mask with canonical base64 pixels, a 512-pixel longest edge, feather in 0–0.05, original SHA-256, exact crop and physical dimensions. The server validates the complete bounded format and binds it to the actual uploaded original and authoritative canvas dimensions. An active mask requires Dots mode; a changed source, crop or size requires a cleared or redrawn selection. This is a manual selection, not automatic subject detection.

The database stores only a private mask asset reference; outlines/pixels are absent from immutable order metadata and analytics. Authenticated saved-design reads return the inline normalized selection for restoration with `Cache-Control: private, no-store`. Server proofs include the mask asset digest even when strength is zero. Every paid package/revision receives its own private mask copy and `source/subject-mask.json` in its private ZIP; its manifest contains the digest and strength only. Design deletion, expiry, failed revision cleanup, abandoned-checkout cleanup and paid artwork erasure include those mask assets, preserving assets referenced by another active owner. Existing database snapshot guards remain unchanged.

Administrator regeneration preserves a selection only while its source/crop/dimensions still match. `clearSubjectMask:true` explicitly removes it in a new revision and resets strength to zero; retaining it across a changed crop returns a conflict. Clearing a saved mask or changing its strength requires new customer proof approval and uses the durable revised-proof notification outbox. Requested replacement photographs always clear the prior mask and strength. Existing original paid snapshots and older revisions remain immutable. The customer must review both new proof views before studio print approval.

## Production packages and review

Checkout renders from the private original image on the server, applies the saved crop, then uses the shared renderer's millimetre geometry. Analysis raster longest edge is fixed at 1000 pixels. Browser Canvas and Sharp interpolation may differ slightly: the server proof is authoritative for printing. Saved finished/template preview responses expose the same `X-Studio-Proof-Hash`; the customer must review both and explicitly approve this hash. Checkout rejects a missing approval or changed production hash before creating any payment session. Archive files include original/cropped sources, previews, exact-size vector SVG, 300-DPI transparent PNG, physical-size PDF, immutable geometry, renderer settings, order identifiers, hashes and manifest. PDF embeds the 300-DPI template raster at exact page dimensions. Package generation happens before charging; files live at unique immutable keys. **No bleed, spot-white separation or printer-specific registration marks are supplied yet; the manifest explicitly declares these limits.** Confirm these with the printer.

Verified webhook fulfilment inserts a paid order once by checkout ID. Repeat webhook deliveries cannot overwrite it. Every order starts in human review. Review source/crop, finished/template, physical dimensions, text, kit contents, warnings and files. Approval applies to one revision. Regeneration appends a new package and clears approval; the paid original snapshot remains immutable. Dispatch requires approval of the current revision and a tracking reference. Line Amplification packages explicitly include a ruler/straight edge. Refunds are performed in Stripe's dashboard at this stage; refund synchronisation and operator UI remain a launch-operation gap.

The manifest records `guideWidthMm` as the effective maximum outline width, shared with SVG generation, plus `requestedGuideWidthMm`; individual paths may remain narrower. Source-quality advice is stored separately as `sourceWarnings` and follows the selected revision's source.

Inverted dark-canvas production is unsupported in the paid workflow. Administrator regeneration rejects `invert:true` before producing or storing a package, even when general physical-validation flags are enabled. Approval and dispatch also reject an existing inverted revision. To repair a historical inverted job, turn inversion off and regenerate; the new immutable revision requires fresh customer proof approval even when its effective guide colour is unchanged. Hold/request-photo actions remain available. The original paid snapshot stays unchanged.

## Requested alternate photographs

The operator's **request-photo** action creates a request tied to the current revision and emails the existing private order-status link. The customer uses that link to upload a JPG/PNG/WebP photo (8 MB, 40 megapixels maximum), adjust its crop and explicitly confirm rights. Size, style, ink, finish and personalisation remain attached to the paid order. Direct-upload tickets are bound to the order and request; a ticket for another order or an ordinary saved design cannot supply replacement artwork. The same save/upload ingress quotas apply, plus three replacement renders and six upload tickets per paid order/hour.

Source validation now reads pixel data as well as headers before saving a design or claiming a replacement lease. Strict decoder warnings reject truncated/corrupt images; the input remains capped at 8 MB/40 MP, single-frame JPEG/PNG/WebP with a usable aspect ratio. Validation produces at most a 256 x 256 RGBA raster in JavaScript and applies a ten-second native processing timeout. This is not a ten-second request or queue-wait guarantee. It does not rewrite or reorient the stored original bytes. Invalid replacement pixels leave an existing lease and staging source unchanged.

If an identical replacement submission claims or finishes while another request is decoding, the losing claim re-authorizes and reads the order once. It returns processing/saved only for the exact matching submission, input hash, request and current artwork state; changed, stale or superseded work remains a conflict. This reconciliation starts no second render and writes no extra assets.

Replacement intake requires a verified paid order, the bearer capability, a current unfulfilled photo request and the expected revision. A ten-minute compare-and-swap lease protects rendering; a UUID submission and payload digest make retries idempotent. The server appends an immutable revision with its own source/package, clears studio approval and returns to `awaiting-review`. The paid snapshot stays unchanged. A concurrent reviewer action or a newer photo request invalidates an in-flight commit. Uncommitted package assets are removed only after confirming that no order revision references them; an uncertain database outcome preserves files for operator reconciliation. Daily retention invalidates interrupted intake leases older than one day and removes their staging source, with the R2 staging lifecycle as a fallback.

Customers must view the stored finished and template proofs and explicitly approve the current revision and snapshot hash on their private status page. The approval is append-only metadata; it does not approve printing. Studio approval and dispatch both reject an unapproved replacement proof. Operator regeneration uses the latest revision's source, preserves its source advice, clears studio approval, and requires a fresh customer proof approval. Dispatched or erased orders cannot accept replacement photos. No real service calls are made by the focused replacement tests.

When administrator regeneration creates a revision with `customerProofRequired=true`, the same order transaction queues one `revised-proof` notification for that revision. Its deterministic notification UUID/provider idempotency key is scoped to the order and revision. After the transaction succeeds, the server attempts delivery. The message reconstructs the existing private fragment link in memory and asks the customer to review both current saved views; no image, source URL, personalised lettering or internal review note is included. Regenerating ordinary artwork that does not require customer proof creates no proof email. Customer-submitted replacement intake already presents its proofs on the open order page; it does not trigger this administrator-regeneration email.

Delivery failure, missing customer email or a missing retained access key leaves a recoverable outbox entry and a saved artwork revision. Use **Retry email** on that entry; do not regenerate to retry delivery. A fresh sending lease prevents simultaneous delivery attempts, and a stored `sent` marker makes later retries a no-op. There is no background email retry scheduler: operators must resolve pending delivery, and restore missing access configuration first. Exactly-once external delivery cannot be guaranteed if provider acceptance was ambiguous and a retry happens after the provider's idempotency window; check provider history before such a late retry.

Creating a newer required proof marks older unsent proof requests `superseded`. Delivery/retry also suppresses a proof request if its revision is no longer current, was already customer-approved, no longer requires proof, or the order is outside active review states. Erased artwork closes all notification delivery. `superseded` is terminal and has no Retry button. A send already accepted or in progress at the provider cannot be recalled; every message explains that its private link always shows the current proof and order status, and server approval still requires the current revision/hash. Current order models have no archive/cancel actions; the proof-mail eligibility allowlist also fails closed for any future or imported terminal status.

## Guest links and privacy lifecycle

Guest save tokens are random 256-bit capabilities; only SHA-256 hashes are persisted. Possession grants access to the design. IDs alone grant nothing. No customer gallery or training path exists. Marketing consent defaults false and is stored separately from the mandatory rights-to-use confirmation. A saved link is intentionally private and should not be pasted into public messages.

Unpaid design links expire after 30 days. `DELETE /api/designs/:id` with its bearer token immediately deletes an uncommitted source and record. Checkouts/order-attached files require an operator review so erasure does not silently destroy paid fulfilment. The admin retention tool removes expired unpaid sources; paid-order erasure removes that order's private source/package assets after dispatch while retaining immutable accounting/audit metadata. Shared legacy sources are retained until other orders no longer need them; the API reports this. Saved project originals have their independent 30-day lifecycle. Snapshot emails are omitted from new checkout records; personalisation remains in immutable artwork metadata. Schedule retention runs on the host and test the retention workflow before launch. Provider backups, server logs and any downloaded printer archives need separate operational retention rules. Set accounting retention with a qualified adviser; do not treat a prototype policy as legal advice.

## API contract

- `GET /api/catalog`: database-driven sizes/finishes plus colours/shipping, prototype and checkout state.
- `POST /api/uploads`: `{mime,bytes}` → `{uploadId,token,url,headers,expiresAt}`. If `catalog.directUploads` is true, PUT the original Blob directly to `url` with exactly `headers`, then save with `source:{uploadId,token}`. This avoids [Vercel's 4.5 MB request/response limits](https://vercel.com/docs/functions/limitations). Local development keeps the base64 request path.
- `POST /api/designs`: `{mode,productId,finishId,inkId,crop:{zoom,x,y,rotation},settings,source:{dataUrl,name},rightsConfirmed:true,marketingConsent:false,email?}`. Returns `{id,token,url,expiresAt,warnings,emailSent}`. The original is immutable; editing creates a new save.
- `GET /api/designs/:id`, `GET /api/designs/:id/source`, `GET /api/designs/:id/preview?view=template`, `DELETE /api/designs/:id`: bearer guest token. The design endpoint returns metadata/settings directly. Previews return SVG and source returns an image blob.
- `POST /api/checkout`: `{designId,token,shippingId,proofApproved:true,proofHash,analyticsConsent?,analyticsSessionId?}` → hosted Stripe URL/order access token or a clear gate/proof error. The proof hash comes only from the authenticated saved-preview response.
- `GET /api/orders/:id`: bearer order token; pending until verified webhook then paid/review status.
- Paid status also includes `replacement:{requestId,revisionId,note,allowed,processing,directUploads}`, `dimensionsMm` and `proof:{revisionId,hash,requiresApproval,approved}`. Capability hashes, storage keys and source pixels are omitted.
- `POST /api/orders/:id/replacement/upload`: bearer order token and `{requestId,expectedRevisionId,mime,bytes}` → the normal direct-upload ticket shape. Its capability is scoped to this order/request. PUT the Blob to its signed URL, then submit the descriptor below.
- `POST /api/orders/:id/replacement`: bearer order token and `{requestId,expectedRevisionId,submissionId:UUID,rightsConfirmed:true,crop,source:{dataUrl,name?}|{uploadId,token}}`. Returns `201 {state:"saved",revisionId,...artworkStatus}` or `202 {state:"processing",...artworkStatus}`. Preserve the exact submission ID/body when retrying an uncertain request; changed input needs a new ID. No arbitrary asset key or renderer settings are accepted.
- `GET /api/orders/:id/proof?revision=:revisionId&view=finished|template`: bearer order token; current immutable proof SVG, with `X-Studio-Proof-Hash`. Add `format=url` to obtain `{url,hash,revisionId,expiresIn}`; local storage returns `url:null`. Signed R2 downloads keep large SVGs outside function response limits.
- `POST /api/orders/:id/proof`: bearer order token and `{revisionId,proofHash,proofApproved:true}`. Records an idempotent customer approval only for the current replacement revision. It cannot set paid status or studio print approval.
- `GET /api/presets?mode=dots`: public `{presets:[{id,version,name,description,mode,settings,rendererVersion}],persistence}`; only current-renderer, published, nonarchived presets in available modes. No administrator or customer metadata. Built-in renderer presets remain available when shared presets are absent.
- `GET /api/admin`: verified administrator bearer JWT (or explicitly enabled loopback QA token); returns `identity:{kind,userId,role}`, orders, counts, configuration and gates.
- `GET /api/admin/presets`: administrator access; `{presets}` with immutable versions and audit history. `POST` accepts `{name,description?,mode,settings}` and returns `201 {preset}` with an unpublished first version. `settings` permits only `PRESET_SETTING_KEYS` from `lib/preset-types.ts`.
- `PATCH /api/admin/presets/:id`: administrator access and `{action,expectedRevision,...}`. `revise` also requires `{name,description?,settings}`; `publish` requires `{version}`; `unpublish`, `archive` and `restore` need no additional fields. All return `{preset}`. Publication/archive actions require operator membership. Stale concurrent edits return 409; no history is overwritten.
- `PATCH /api/admin/orders/:id`: `{action,note,revision?,settings?,crop?,tracking?}`; actions approve, hold, request-photo, regenerate, dispatch. Customer-message actions additionally return `{notification:{id,type,status,message}}`. Retry with `{action:"retry-notification",notificationId,revision?}`; it is permitted after dispatch, does not repeat fulfilment, and becomes a no-op once the notification is sent. `orders[].notifications` exposes durable delivery state and attempt counts for the private admin UI.
- Regeneration needing customer proof additionally returns a `revised-proof` notification. Its stored entry includes `revisionId`; statuses are `pending`, `sending`, `sent` or terminal `superseded`. Retrying an obsolete proof request returns `superseded` without contacting the mail provider. Notification metadata stores no raw guest capability or private link.
- `GET /api/admin/orders/:id/files?file=source|finished|template|archive&revision=:currentRevisionId`: verified administrator bearer credential and the exact revision being reviewed. Missing or stale revisions return 409 before any asset is read or signed. Refresh the desk and inspect the current proofs after a conflict. Never link directly to object keys.
- Add `&format=url` to that revision-bound endpoint for `{url,expiresIn:60,revisionId}` on R2 or `{url:null,local:true,revisionId}` locally. Navigate to the signed archive URL so large ZIP files avoid function response limits. A signed URL targets the immutable package of the checked revision. Source/preview fetching from signed storage requires the configured CORS policy.
- `POST /api/admin/retention`: operator membership and same-origin header; erases expired unpaid, unattached designs. Scheduling is an operator deployment task, not enabled automatically.
- `DELETE /api/admin/orders/:id/assets`: `{note}` plus operator membership; deletes source/package files after dispatch. Retains immutable snapshot metadata (including personalisation), audit and accounting records. Full data-subject erasure needs a separate legal/operational review of that retained data and provider backups.
- `POST /api/analytics`: strict opt-in `{consent:true,sessionId,events}` metadata only; rejects source, text, email, tokens and client-supplied payment events. Sessions are daily rotating keyed pseudonyms. `admin.analytics` aggregates event/unique-day-session counts by mode and size for the last 30 days; it does not expose identifiers. Only a verified webhook records payment completion, and only when the checkout included analytics consent. Opt-in sampling means this is not a count of every visitor/order.

Mutation routes require an exact same-origin `Origin` header. Private responses use `Cache-Control: private, no-store`. Configure observability to redact Authorization, fragment-bearing redirects, uploaded bodies and Stripe/Resend payloads. Mail and payment provider acceptance, production Supabase migrations/RLS and R2 privacy still need integration checks with real service credentials.
