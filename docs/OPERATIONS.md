# Operating Slow Reveal Studio

## Current safety boundary

The studio is a prototype until real canvas/ink/marker tests, costs, packaging and operational checks are approved. Example prices are development fixtures. Setting flags is an operator assertion, not evidence that physical tests passed. The app cannot validate a physical product remotely. Labs and private design saving work without payment services. Production checkout fails closed unless every service and physical gate is configured and the database catalogue is approved.

## Local development

Copy `.env.example` to `.env.local`. Generate a private administrator token of at least 32 base64url characters and enter it in `/admin`. No default password or unauthenticated administrator route exists, even on localhost. Run `npm run dev`; bind to loopback. Saved photos and records are under `.data/`, outside `public/`, ignored by Git. Do not put this folder on a public share or deploy its contents. This adapter is single-process development storage. Production requires Supabase and R2; `ALLOW_LOCAL_DEVELOPMENT_STORAGE` is only an explicit opt-in for local production-build testing.

## Deployment configuration

1. Create a Supabase project and apply all migrations in `supabase/migrations/`, including `202609270003_customer_proofs.sql` for append-only customer proof attestations. Keep the service-role credential server-only. All app tables have RLS enabled and anonymous/authenticated privileges revoked. The HTTP API owns access control. The optional admin-user table reserves a future per-user auth flow; current operations use a high-entropy operator bearer token.
2. Create an R2 bucket with all public access disabled. Scope its token to this bucket. Supply the four R2 environment variables. Allow CORS GET/HEAD/PUT from the exact website origin and the `Content-Type`, `Content-Length`, `If-None-Match` request headers. No permanent public photo URLs are created. Authenticated source/file requests redirect to signed GET URLs valid for 60 seconds; treat those temporary URLs as private capabilities. Large originals use a two-minute presigned upload ticket and a 15-minute finalisation window. Finalisation rechecks bytes, magic signature, MIME, decoded dimensions and ownership before copying to a permanent immutable source. Configure an R2 lifecycle rule to expire `staging/` after one day as a fallback for abandoned or late upload tickets.
3. Configure Resend with a verified sending domain and `RESEND_FROM_EMAIL`. Check spam handling and customer-support replies. Saved-design email is sent only if an email address is explicitly supplied to save. Order/dispatch/request-photo mail uses plain text and a durable notification record with a stable provider idempotency key. A failed dispatch or photo-request email returns `notification.status:pending` while preserving the successful order update; operators retry that notification without repeating dispatch. Confirmations retry through Stripe webhook retries or the same operator action. Persisted sent markers prevent later webhook replays from resending old confirmation messages, even after the provider's own idempotency window. No tests send real email.
4. Configure Stripe, with a distinct test and live setup. Point its webhook to `/api/stripe/webhook`; subscribe to `checkout.session.completed` and `checkout.session.async_payment_succeeded`. Raw body signatures are verified, then session identity, snapshot hash, currency and amount are checked. Session redirects never create a paid order. Test duplicate delivery, delayed methods, invalid signatures, checkout retries and mail-provider failures before enabling real money.
5. Replace prototype catalogue costs and finishes in `studio_catalogue.definition`. Review UK tax and delivery treatment, establish inventory, and set `prototype:false` only after commercial approval. Prices in requests are ignored; the server quotes from this catalogue. Fixed UK shipping tiers are £5.95/£9.95 development values; update the authoritative catalogue code before launch. Stripe promotion codes are supported; the verified discount is checked against the quoted total.
6. Set a canonical HTTPS `NEXT_PUBLIC_SITE_URL`, complete physical tests, record their evidence, then set `PHYSICAL_VALIDATION_APPROVED=true`, appropriate `PHYSICALLY_VALIDATED_MODES` and `LIVE_CHECKOUT_ENABLED=true`. Inverted/dark-canvas checkout remains blocked because a white-ink production separation is not implemented. Never enable a mode solely because its screen preview looks attractive.
7. Configure `RATE_LIMIT_SECRET` and host-level request/body limits before public access. Ingress must replace client-supplied forwarding headers. The server uses daily keyed hashes of an ingress IP, never stores/logs raw IP addresses, and enforces atomic Supabase quotas: ten saves/uploads per 15 minutes, 60 expensive previews per 15 minutes, and 200 saves/upload tickets per deployment/day. Checkout is limited before heavy production rendering: five attempts per ingress IP/15 minutes, 50 per deployment/day, and three per saved design/hour. Local development uses bounded in-memory counters. These small initial quotas protect the prototype; tune deliberately after measured use. Save endpoints cap image uploads at 8 MB and 40 megapixels, reject MIME/signature mismatches, and reject animated or extreme-aspect inputs. Same-origin checking is CSRF protection, not bot protection. No image data, customer details or secrets are logged by app handlers.
8. Configure a separate random `CRON_SECRET` and schedule `GET /api/cron/retention` daily (for example 04:00 UTC), with `Authorization: Bearer <CRON_SECRET>`. Vercel cron adds this header from its environment. The job deletes expired staging tickets, analytics older than 90 days, expired unpaid designs and abandoned checkouts only after Stripe confirms the session is expired and unpaid (seven-day grace). Unknown sessions stay for manual review. A configured secret alone does not prove the scheduler ran: verify the first execution and monitor failures. Paid sources are copied into per-order/revision storage so erasure cannot break another order. Legacy shared references are preserved if any other checkout/order still needs them.
9. Configure `ORDER_ACCESS_KEYS` as a server-only JSON keyring, for example `{"v1":"<independent random secret of at least 32 characters>"}`, and set `ORDER_ACCESS_KEY_ID=v1`. New order capabilities are HMAC-SHA-256 values derived from the order ID and selected key; the database stores only a key ID and capability hash. Confirmation/status messages reconstruct the private `/order/:id#token=...` link in memory when sending, so the outbox never stores raw access tokens. For rotation, add a new named key, change the active ID, and retain earlier keys while their orders need email access. Replacing/removing an old key prevents reconstruction of those old links; restore it from secure secret storage before retrying notifications. Existing customer links still authenticate against their recorded hashes. Never log environment keyrings or email bodies. Legacy development orders without a retained key ID need manual access-link recovery rather than inventing a new token.

## Production packages and review

Checkout renders from the private original image on the server, applies the saved crop, then uses the shared renderer's millimetre geometry. Analysis raster longest edge is fixed at 1000 pixels. Browser Canvas and Sharp interpolation may differ slightly: the server proof is authoritative for printing. Saved finished/template preview responses expose the same `X-Studio-Proof-Hash`; the customer must review both and explicitly approve this hash. Checkout rejects a missing approval or changed production hash before creating any payment session. Archive files include original/cropped sources, previews, exact-size vector SVG, 300-DPI transparent PNG, physical-size PDF, immutable geometry, renderer settings, order identifiers, hashes and manifest. PDF embeds the 300-DPI template raster at exact page dimensions. Package generation happens before charging; files live at unique immutable keys. **No bleed, spot-white separation or printer-specific registration marks are supplied yet; the manifest explicitly declares these limits.** Confirm these with the printer.

Verified webhook fulfilment inserts a paid order once by checkout ID. Repeat webhook deliveries cannot overwrite it. Every order starts in human review. Review source/crop, finished/template, physical dimensions, text, kit contents, warnings and files. Approval applies to one revision. Regeneration appends a new package and clears approval; the paid original snapshot remains immutable. Dispatch requires approval of the current revision and a tracking reference. Line Amplification packages explicitly include a ruler/straight edge. Refunds are performed in Stripe's dashboard at this stage; refund synchronisation and operator UI remain a launch-operation gap.

The manifest records `guideWidthMm` as the effective maximum outline width, shared with SVG generation, plus `requestedGuideWidthMm`; individual paths may remain narrower. Source-quality advice is stored separately as `sourceWarnings` and follows the selected revision's source.

## Requested alternate photographs

The operator's **request-photo** action creates a request tied to the current revision and emails the existing private order-status link. The customer uses that link to upload a JPG/PNG/WebP photo (8 MB, 40 megapixels maximum), adjust its crop and explicitly confirm rights. Size, style, ink, finish and personalisation remain attached to the paid order. Direct-upload tickets are bound to the order and request; a ticket for another order or an ordinary saved design cannot supply replacement artwork. The same save/upload ingress quotas apply, plus three replacement renders and six upload tickets per paid order/hour.

Replacement intake requires a verified paid order, the bearer capability, a current unfulfilled photo request and the expected revision. A ten-minute compare-and-swap lease protects rendering; a UUID submission and payload digest make retries idempotent. The server appends an immutable revision with its own source/package, clears studio approval and returns to `awaiting-review`. The paid snapshot stays unchanged. A concurrent reviewer action or a newer photo request invalidates an in-flight commit. Uncommitted package assets are removed only after confirming that no order revision references them; an uncertain database outcome preserves files for operator reconciliation. Daily retention invalidates interrupted intake leases older than one day and removes their staging source, with the R2 staging lifecycle as a fallback.

Customers must view the stored finished and template proofs and explicitly approve the current revision and snapshot hash on their private status page. The approval is append-only metadata; it does not approve printing. Studio approval and dispatch both reject an unapproved replacement proof. Operator regeneration uses the latest revision's source, preserves its source advice, clears studio approval, and requires a fresh customer proof approval. Operators should tell the customer to revisit their private order link after regeneration; automatic revised-proof notification is not currently sent. Dispatched or erased orders cannot accept replacement photos. No real service calls are made by the focused replacement tests.

## Guest links and privacy lifecycle

Guest save tokens are random 256-bit capabilities; only SHA-256 hashes are persisted. Possession grants access to the design. IDs alone grant nothing. No customer gallery or training path exists. Marketing consent defaults false and is stored separately from the mandatory rights-to-use confirmation. A saved link is intentionally private and should not be pasted into public messages.

Unpaid design links expire after 30 days. `DELETE /api/designs/:id` with its bearer token immediately deletes an uncommitted source and record. Checkouts/order-attached files require an operator review so erasure does not silently destroy paid fulfilment. The admin retention tool removes expired unpaid sources; paid-order erasure removes that order's private source/package assets after dispatch while retaining immutable accounting/audit metadata. Shared legacy sources are retained until other orders no longer need them; the API reports this. Saved project originals have their independent 30-day lifecycle. Snapshot emails are omitted from new checkout records; personalisation remains in immutable artwork metadata. Schedule retention runs on the host and test the retention workflow before launch. Provider backups, server logs and any downloaded printer archives need separate operational retention rules. Set accounting retention with a qualified adviser; do not treat a prototype policy as legal advice.

## API contract

- `GET /api/catalog`: database-driven sizes/finishes plus colours/shipping, prototype and checkout state.
- `POST /api/uploads`: `{mime,bytes}` → `{uploadId,token,url,headers,expiresAt}`. If `catalog.directUploads` is true, PUT the original Blob directly to `url` with exactly `headers`, then save with `source:{uploadId,token}`. This avoids [Vercel's 4.5 MB request/response limits](https://vercel.com/docs/functions/limitations). Local development keeps the base64 request path.
- `POST /api/designs`: `{mode,productId,finishId,inkId,crop:{zoom,x,y,rotation},settings,source:{dataUrl,name},rightsConfirmed:true,marketingConsent:false,email?}`. Returns `{id,token,url,expiresAt,warnings,emailSent}`. The original is immutable; editing creates a new save.
- `GET /api/designs/:id`, `GET /api/designs/:id/source`, `GET /api/designs/:id/preview?view=template`, `DELETE /api/designs/:id`: bearer guest token. The design endpoint returns metadata/settings directly. Previews return SVG and source returns an image blob.
- `POST /api/checkout`: `{designId,token,shippingId,proofApproved:true,proofHash,analyticsConsent?,analyticsSessionId?}` → hosted Stripe URL/order access token or a clear gate/proof error. The proof hash comes only from the authenticated saved-preview response.
- `GET /api/orders/:id`: bearer order token; pending until verified webhook then paid/review status.
- Paid status also includes `replacement:{requestId,revisionId,note,allowed,processing,directUploads}`, `dimensionsMm` and `proof:{revisionId,hash,requiresApproval,approved}`. Capability hashes, storage keys and source pixels are omitted.
- `POST /api/orders/:id/replacement/upload`: bearer order token and `{requestId,expectedRevisionId,mime,bytes}` → the normal direct-upload ticket shape. Its capability is scoped to this order/request. PUT the Blob to its signed URL, then submit the descriptor below.
- `POST /api/orders/:id/replacement`: bearer order token and `{requestId,expectedRevisionId,submissionId:UUID,rightsConfirmed:true,crop,source:{dataUrl,name?}|{uploadId,token}}`. Returns `201 {state:"saved",revisionId,...artworkStatus}` or `202 {state:"processing",...artworkStatus}`. Preserve the exact submission ID/body when retrying an uncertain request; changed input needs a new ID. No arbitrary asset key or renderer settings are accepted.
- `GET /api/orders/:id/proof?revision=:revisionId&view=finished|template`: bearer order token; current immutable proof SVG, with `X-Studio-Proof-Hash`. Add `format=url` to obtain `{url,hash,revisionId,expiresIn}`; local storage returns `url:null`. Signed R2 downloads keep large SVGs outside function response limits.
- `POST /api/orders/:id/proof`: bearer order token and `{revisionId,proofHash,proofApproved:true}`. Records an idempotent customer approval only for the current replacement revision. It cannot set paid status or studio print approval.
- `GET /api/admin`: bearer operator token; orders, counts, configuration and gates.
- `PATCH /api/admin/orders/:id`: `{action,note,revision?,settings?,crop?,tracking?}`; actions approve, hold, request-photo, regenerate, dispatch. Customer-message actions additionally return `{notification:{id,type,status,message}}`. Retry with `{action:"retry-notification",notificationId,revision?}`; it is permitted after dispatch, does not repeat fulfilment, and becomes a no-op once the notification is sent. `orders[].notifications` exposes durable delivery state and attempt counts for the private admin UI.
- `GET /api/admin/orders/:id/files?file=source|finished|template|archive`: bearer operator token, private asset stream. Never link directly to object keys.
- Add `&format=url` to the files endpoint for `{url,expiresIn:60}` on R2 or `{url:null,local:true}` locally. Navigate to the signed archive URL so large ZIP files avoid function response limits. Source/preview fetching from signed storage requires the configured CORS policy.
- `POST /api/admin/retention`: operator token and same-origin header; erases expired unpaid, unattached designs. Scheduling is an operator deployment task, not enabled automatically.
- `DELETE /api/admin/orders/:id/assets`: `{note}` plus operator token; deletes source/package files after dispatch. Retains immutable snapshot metadata (including personalisation), audit and accounting records. Full data-subject erasure needs a separate legal/operational review of that retained data and provider backups.
- `POST /api/analytics`: strict opt-in `{consent:true,sessionId,events}` metadata only; rejects source, text, email, tokens and client-supplied payment events. Sessions are daily rotating keyed pseudonyms. `admin.analytics` aggregates event/unique-day-session counts by mode and size for the last 30 days; it does not expose identifiers. Only a verified webhook records payment completion, and only when the checkout included analytics consent. Opt-in sampling means this is not a count of every visitor/order.

Mutation routes require an exact same-origin `Origin` header. Private responses use `Cache-Control: private, no-store`. Configure observability to redact Authorization, fragment-bearing redirects, uploaded bodies and Stripe/Resend payloads. Mail and payment provider acceptance, production Supabase migrations/RLS and R2 privacy still need integration checks with real service credentials.
